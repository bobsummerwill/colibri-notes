
## Summary

DeepSeek V4 on CUDA can use a second GPU as an expert-mirror tier. With `DSV4_CUDA_PEER_DEVICE=1`, that GPU holds more expert mirrors and computes them itself over NVLink, for a model that doesn't fit on one card. A second change, VRAM-first lookups, helps on one GPU too.

On 2x RTX 3090 against dev:
- REAP-150B decodes 1.44x faster with both GPUs.
- The full V4 Flash decodes 1.27x faster.
- Time to first token is unchanged.
- Every answer is byte-identical to dev's.

**Opt-in switches:**
- `V4_GPU_RESIDENT_FIRST=1`: an expert already mirrored in VRAM is computed from the mirror without a RAM-store lookup.
  - The store still records the routing (history, HITS, heat).
  - Its RAM pin ranking leaves mirrored experts out, so RAM holds the experts that aren't in VRAM.
- `DSV4_CUDA_PEER_DEVICE=N`: a second mirror pool on GPU N.
  - It needs peer access both ways, e.g. NVLink. Without it, the pool stays off with a warning and decode runs on the primary GPU.
  - `DSV4_CUDA_PEER_COMPUTE` (default 1) runs the experts mirrored there on that GPU, bit-identically.
  - GPU N is probed before it is touched, and a failed init is rolled back.
- `DSV4_CUDA_PIN_CAP_GB` caps the page-locked expert slabs. The default is unchanged, 20 GiB.
- `V4_SERVE_STATS_LOG=1` prints per-turn decode stats and decode-MoE counters.

**Two changes apply with every switch off:**
- **Each mirror cache keeps its own growth guard,** because the peer pool has its own card, free VRAM and reserve. It keeps dev's rule, with one difference:
  - Below 32 live mirrors, the bank-sized default keeps its 64-mirror probe margin, where dev gives it none.
  - That phase only matters on a card too small for the bank; `docs/deepseek-v4.md` says so.
  - A failed mirror upload rolls its slot back instead of leaving a dead entry.
- **A sticky CUDA fault no longer fails every later request.** A launch failure, such as a trap on the peer GPU, is sticky for the process's whole CUDA context, device 0 included. The engine now turns CUDA off for the process (`dsv4_cuda_lost()`):
  - mirror lookups miss;
  - the decode MoE takes host copies;
  - the attention's grouped `wo_a` matvec falls back to the CPU;
  - a failed decode block names its stage and keeps the inner error.

  The faulted request and every later one finish on the host, at host speed, until restart.

## Measurements

**Setup.**
- 2x RTX 3090 24 GB with an NVLink bridge, Ryzen 9 9950X3D, 62 GB, CUDA 12.0.
- Build: `make -f Makefile.deepseek-v4 deepseek-v4 CUDA=1 CUDA_ARCH=sm_86 NO_TC=1`.
- Serve: `--ram 40 --ctx 8192`, `COLI_CUDA_MOE_BATCH=1`, greedy.
- Each sample starts a fresh server, and arms are interleaved.
- dev is c1c06ac6, and this PR is its 11 commits on top.
- Decode is the mean over a sample's answers, then the median over samples.

| | REAP-150B, 1 GPU | REAP-150B, 2 GPUs | V4 Flash, 1 GPU | V4 Flash, 2 GPUs |
|---|---|---|---|---|
| dev | 3.010 tok/s | | 2.646 tok/s | |
| this PR | 3.098 (1.03x) | 4.332 (**1.44x**) | 2.697 (1.02x) | 3.357 (**1.27x**) |

- **"1 GPU"** is `V4_GPU_RESIDENT_FIRST=1`. **"2 GPUs"** adds `DSV4_CUDA_PEER_DEVICE=1`.
- **REAP:** 6 prompts x 300 tokens, 2 samples per arm. A second session matched within 0.3%.
- **V4 Flash:** 3 open-ended prompts x 300 tokens, 1 sample per arm.
  - The second GPU speeds up each prompt by 1.23-1.27x.
  - GPU 1 fills to 23 GB, almost all of it mirrors.
- **Time to first token is the same as dev's.** On long prompts (1,992 and 3,005 tokens), both reach the first token in 86 s and 124 s, one GPU or two. On REAP it is 3.6-3.9 s against dev's 3.6 s.
- **Where the one-GPU gain comes from.** I measured the commits in four steps (REAP, one GPU, 2 samples each):

  | step | vs dev |
  |---|---|
  | the guard | 1.000x |
  | + pin cap and stats log | 1.002x |
  | + VRAM-first | 1.031x |
  | + peer tier and fault handling, peer off | 1.031x |

  - So VRAM-first gives all of it, and the always-on changes cost nothing measurable.
- **Other backends are unchanged.**
  - On one RTX 5070 12 GB (sm_120, full V4 Flash, default settings), decode is 1.00-1.02x dev.
  - CPU-only decode is the same as dev's.
  - Vulkan is untouched.
- **Fault test:** `DSV4_CUDA_PEER_FAULT=3000:sticky` injects a sticky fault on the peer GPU at the 3000th pass, in a server answering six prompts.
  - All six finish with 300 tokens each, on the host after the fault, with no hang.
  - Before the latch, every request after the fault failed until restart.
  - This ran on the previous dev base. The patches are unchanged since.

  - #1766's kernels make each GPU faster.
  - On these cards, this PR's peer tier gets more from the second GPU than the layer split does: 6.07 against 4.82 tok/s on REAP.
- **The two multi-GPU modes are alternatives.** Both claim GPU 1, so `DSV4_CUDA_DEVICES` and `DSV4_CUDA_PEER_DEVICE` shouldn't be set together.
  - `DSV4_CUDA_VRAM_RESERVE_MB` is #1766's preload reserve there and dev's mirror-growth reserve here.
- **The merge** is [`e2933955`](https://github.com/bobsummerwill/colibri/commits/e2933955) on my fork. It carries two fixes to #1766's code, both described on #1766:
