## 1. Your question: the default configuration on the full V4 Flash

No `COLI_CUDA_MOE_BATCH`, full `deepseek-ai/DeepSeek-V4-Flash-0731` (256 experts), dev 7df8c27c against this branch (b286167e), prompt and decode, interleaved W A B B A A B (W discarded), a fresh server per sample, greedy:

| build | 1,992-token TTFT (dev → branch) | 3,005-token TTFT | decode | texts |
|---|---|---|---|---|
| generic CUDA, 2× RTX 3090, CUDA 12.0 | 160.9 → 158.2 s (0.983×) | 264.6 → 261.5 s (0.989×) | equal (within 1%) | byte-identical, all 6 samples |
| DeepGEMM sm_120a, RTX 5070 12 GB, CUDA 12.8 | 242.6 → 242.3 s (0.999×) | 373.1 → 374.4 s (1.004×) | equal (within 1%) | byte-identical, all 6 samples |

`DSV4_MM_WARP_VERIFY=1` on the same configuration ran the old and new kernels side by side for 1,500 `mm_batch` calls: 0 mismatching bits. So by the rule you gave, `DSV4_MM_WARP` stays on by default. Manifests (validated with `c/experiment_manifest.py`): [final6](https://github.com/bobsummerwill/colibri-notes/tree/c402853ba03b9af99fa52e46eede6acd9062bba8/manifests/final6) (`pr1-default-1992/3005`), [final6-c4ab](https://github.com/bobsummerwill/colibri-notes/tree/c402853ba03b9af99fa52e46eede6acd9062bba8/manifests/final6-c4ab) (`pr1-deepgemm-1992/3005`).

**Compressed-KV fallbacks, in full.** At 24 GB and below, dev's default configuration can run out of VRAM for the compressed-KV buffer: once the decode mirrors have taken VRAM down to the 600 MiB reserve, `dsv4_cuda_kv_comp_append` cannot grow it (`[DSV4 CUDA] kv comp allocation: out of memory`), `coli_v4_gpu_kv_cache_sync` returns 0 and that layer's attention runs on the CPU. CPU and CUDA attention do not give the same bits, so a greedy text can change. The count varies from run to run, and this branch does not change that code. What the runs had:

- **2× RTX 3090 (the table's first row):** every sample of both arms, warm-up included, logged 252 of these fallbacks (the `_VERIFY` run 420). Same count everywhere, same texts.
- **RTX 5070, first round (the table's second row):** dev's samples had none. The branch's sample 2 alone had 421 handled allocation failures (1 weight, 420 kv comp), a GPU0 peak of 11,747 MiB against ~11,255, and a 3k-token TTFT of 409 s against ~373; the VRAM before that sample was the same as for the others, and I did not find the cause. Its texts were identical, and the medians above include it.
- **RTX 5070, second round** (W + 3 more pairs): TTFT 0.998× / 0.995×, but **two of its seven runs changed prompt 2's text**: dev's sample 1 (1,066 fallbacks, `e79e1278…`) and the branch's warm-up run (458 fallbacks, `f0baf6ae…`; discarded from the timings, not from this count), against the reference `8b3f437b…`. The other five (dev 2, branch 3) gave the reference texts.
- **RTX 5070, controls:** with `DSV4_CUDA_VRAM_RESERVE_MB=2000`, dev ×2 and branch ×2 had 0 fallbacks, the reference texts and the normal prompt-2 TTFT (373-375 s, against ~410 s with fallbacks). With all attention on the CPU (`COLI_CUDA_ATTN_BATCH=0`), dev and the branch are byte-identical to each other, and differ from the GPU-attention texts on both prompts. So the changed texts come from where attention runs, not from this branch.

Evidence for the second round and the controls: [final8-c4ab](https://github.com/bobsummerwill/colibri-notes/tree/c402853ba03b9af99fa52e46eede6acd9062bba8/manifests/final8-c4ab) (c4ab2, c4ab3). A 2 GB reserve avoids the fallbacks. I can open an issue for this if useful.

## 2. The bank (`COLI_CUDA_MOE_BATCH=1`), full model, 2× RTX 3090

- **Like for like:** dev given the ~4700 MiB reserve its own comment recommends for the bank (`DSV4_CUDA_VRAM_RESERVE_MB=4681`, the size this branch computes), 3 samples each: TTFT 129.2 → 85.9 s (0.665×) and 187.2 → 123.4 s (0.659×), decode equal, texts identical, 0 fallbacks.

Against that the branch would be 0.48× on prompt 2; that is not a like-for-like comparison, so the figure above is the one I'd quote.
- Double bank against the single bank (branch only, 3 samples): 0.775× / 0.822×.
- One sample each: ~16k-token prompt with the bank on both sides 1151 → 795 s (0.69×); ~8k-token prompt in the default configuration 0.982×; MTP drafting with the bank 0.665×; a speculative batch and two requests at once both gave the sequential texts.

## 3. The 150B REAP checkpoint, CUDA and Vulkan (2× RTX 3090)

- **CUDA only, bank against dev's union, same reserve:** 0.595× / 0.542×, one sample each, texts identical.
- **Pure Vulkan:** with its default host pool (sized from free RAM at start: 16.75 GiB here) the process was OOM-killed after prompt 1, on the branch once and on dev once, and dev was killed again with the pool set to 15.75 GiB. With the pool at 12 GiB and the CPU/GPU split pinned: dev ×3 and branch ×3 byte-identical, TTFT 1.001× / 0.985×. With only the pool at 12 GiB (split left to run time): dev ×3 and branch ×2 byte-identical and equal to the CUDA path's texts, TTFT 0.998× / 0.997×. Even at 12 GiB, MemAvailable fell to about 0.5 GiB.
- **Vulkan + CUDA, no bank, one 3,100 MiB reserve for all:** dev ×4 (two environments) and branch ×2, 6 of 6 identical, 0.98×. In an earlier run where the branch had only dev's 600 MiB reserve, it had 1,340 kv comp fallbacks and a different text (the mechanism in section 1).
- **Vulkan + CUDA with this branch's bank** (×2): 0.588× / 0.537×, but prompt 2 gives the CUDA-only text (`1f019203…`) rather than the Vulkan + CUDA union path's (`1bdc5d70…`). My reading, not proven: in a Vulkan build dev's union prefill runs some experts through Vulkan, while the bank runs them all on CUDA. dev refuses the bank on this checkpoint, so there is no dev bank arm to compare against.
