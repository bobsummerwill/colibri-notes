`DSV4_MM_WARP_VERIFY=1` on the same configuration ran the old and new kernels side by side for 1,500 `mm_batch` calls:
0 mismatching bits. So by the rule you gave it stays on by default. Manifests (validated with
`c/experiment_manifest.py`): [final6](https://github.com/bobsummerwill/colibri-notes/tree/2e02c016ecacf3f388faadbf822b550b465fdef5/manifests/final6)
(`pr1-default-1992/3005`), [DeepGEMM](https://github.com/bobsummerwill/colibri-notes/tree/2e02c016ecacf3f388faadbf822b550b465fdef5/manifests/final6-c4ab)
(`pr1-deepgemm-1992/3005`). A second round on the RTX 5070 (W + 3 more pairs) gave 0.998× / 0.995×, but not identical
texts throughout: two of its seven runs changed prompt 2, dev's sample 1 (`e79e1278…`) and the branch's warm-up run
(`f0baf6ae…`, discarded from the timings but not from this count). Both had kv comp fallbacks (see the end); the other
five (dev 2, branch 3) gave the reference texts. A third round with a 2 GB reserve had 0 fallbacks and gave the
reference texts on both trees, and with all attention forced to the CPU (`COLI_CUDA_ATTN_BATCH=0`) dev and the branch are
byte-identical to each other, so the change comes from where attention runs, not from this branch. Evidence:
[final8-c4ab](https://github.com/bobsummerwill/colibri-notes/tree/2e02c016ecacf3f388faadbf822b550b465fdef5/manifests/final8-c4ab) (c4ab2, c4ab3).

With the bank (`COLI_CUDA_MOE_BATCH=1`), full model, dev given the ~4700 MiB reserve its own comment recommends for the
bank (`DSV4_CUDA_VRAM_RESERVE_MB=4681`, the size this branch computes; with the 2800 MiB default, dev's bank is refused
on the second prompt once decode mirrors have grown): TTFT 129.2 → 85.9 s (0.665×) and 187.2 → 123.4 s (0.659×), decode
equal, texts identical, 3 samples each. ~16k-token prompt with the bank: 1151 → 795 s (0.69×). On the 150B REAP
checkpoint: 0.54-0.60×.

Vulkan builds (REAP checkpoint, 2× RTX 3090): pure Vulkan with the host pool capped at 12 GiB (left to its default, the
pool is sized from free RAM at start and the process is OOM-killed, dev and branch alike), dev against the branch, 5 of 5
samples byte-identical (and equal to the CUDA path's texts), TTFT 0.998× / 0.997×. Vulkan + CUDA with the same reserve,
no bank: 6 of 6 identical, 0.98×. With this branch's bank on Vulkan + CUDA (0.59× / 0.54×), prompt 2 gives the CUDA-only
text rather than the Vulkan + CUDA union path's; I have not pinned down why the union path differs there.

Since the review: b286167e drops two unused variables in the DeepGEMM kernels (upstream code; the first DeepGEMM build
here warned about them; generic builds do not compile those functions), and dev 61646cbd is merged in (47c8ec51, no
conflicts; `make check` passes, CUDA build clean, CI green). The GPU numbers above are from before that merge; dev's new
commits touch no DeepSeek V4 CUDA file.

One thing that is dev's behaviour, not this branch's: in the default configuration at 24 GB and below, decode mirrors can
leave too little VRAM for the compressed-KV buffer (`[DSV4 CUDA] kv comp allocation: out of memory`). That layer's
attention then runs on the CPU, which rounds differently, so a greedy text can change between runs. A 2 GB
`DSV4_CUDA_VRAM_RESERVE_MB` avoids it. I can open an issue for it if useful.
