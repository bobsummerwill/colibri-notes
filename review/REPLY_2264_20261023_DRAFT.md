The full-model measurement you asked for is done. In the default configuration (no `COLI_CUDA_MOE_BATCH`), on the full
`deepseek-ai/DeepSeek-V4-Flash-0731` (256 experts), dev 7df8c27c against this branch, prompt and decode, interleaved
(W A B B A A B, W discarded, a fresh server per sample, greedy):

| build | 1,992-token TTFT (dev → branch) | 3,005-token TTFT | decode | texts |
|---|---|---|---|---|
| generic CUDA, 2× RTX 3090, CUDA 12.0 | 160.9 → 158.2 s (0.983×) | 264.6 → 261.5 s (0.989×) | 1.002× | byte-identical, all 6 samples |
| DeepGEMM sm_120a, RTX 5070, CUDA 12.8 | 242.6 → 242.3 s (0.999×) | 373.1 → 374.4 s (1.004×) | 1.002× | byte-identical, all 6 samples |

`DSV4_MM_WARP_VERIFY=1` on the same configuration ran the old and new kernels side by side for 1,500 `mm_batch` calls:
0 mismatching bits. So by the rule you gave it stays on by default. Manifests (validated with
`c/experiment_manifest.py`): [final6](https://github.com/bobsummerwill/colibri-notes/tree/<NOTES_SHA>/manifests/final6)
(`pr1-default-1992/3005`), [DeepGEMM](https://github.com/bobsummerwill/colibri-notes/tree/<NOTES_SHA>/manifests/final6-c4ab)
(`pr1-deepgemm-1992/3005`).

Also on the full model, with the bank (`COLI_CUDA_MOE_BATCH=1`): dev with the reserve its own comment recommends
for the bank (`DSV4_CUDA_VRAM_RESERVE_MB=4681`; with the 2800 MiB default dev's bank is refused on the second prompt
once decode mirrors have grown) against this branch: TTFT 129.2 → 85.9 s (0.665×) and 187.2 → 123.4 s (0.659×), decode
equal, texts identical, 3 samples each. ~16k-token prompt with the bank: 1151 → 795 s (0.69×).

One commit added since the review: b286167e drops two unused variables in the DeepGEMM kernels (upstream code; the
first DeepGEMM build here warned about them). Generic builds do not compile those functions.

Two things we ran into that are dev's behaviour, not this branch's (same on both, details in the notes if useful):
- In the default configuration at 24 GB and below, decode mirrors can leave too little VRAM for the compressed-KV
  buffer (`[DSV4 CUDA] kv comp allocation: out of memory`); that layer's attention then runs on the CPU, which does not
  round like the CUDA path, so a greedy text can change. A 2 GB `DSV4_CUDA_VRAM_RESERVE_MB` avoids it.
- Pure Vulkan with `--ram 40` on a 62 GB box: the tier's host pool is sized from free RAM at start, beside the RAM
  cache, and can get the server OOM-killed.
