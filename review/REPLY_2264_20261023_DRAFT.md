Since the review: b286167e drops two unused variables in the DeepGEMM kernels (upstream code; the first DeepGEMM build
here warned about them; generic builds do not compile those functions), and dev 61646cbd is merged in (47c8ec51, no
conflicts; `make check` passes, CUDA build clean).

One thing we ran into that is dev's behaviour, not this branch's, and that matters for anyone comparing texts: in the
default configuration at 24 GB and below, decode mirrors can leave too little VRAM for the compressed-KV buffer
(`[DSV4 CUDA] kv comp allocation: out of memory`); that layer's attention then runs on the CPU, which does not round
like the CUDA path, so a greedy text can change from run to run (dev and branch alike). A 2 GB
`DSV4_CUDA_VRAM_RESERVE_MB` avoids it (0 fallbacks, reference texts). I can open an issue for it if useful.
