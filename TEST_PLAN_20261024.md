## Why
The #2264 reply ([comment](https://github.com/JustVugg/colibri/pull/2264#issuecomment-6380394089)) left two Vulkan
items open, both on the REAP-150B checkpoint, 2× RTX 3090:

1. **Pure Vulkan, default host pool.** In final6, final7 and final8, the default pool OOM-killed the server after
   prompt 1, on dev and on PR #1. The pool was sized from the free RAM at start, so this was upstream's problem.
   Every clean Vulkan result pinned the pool at 12 GiB. Since then, dev 61646cbd brought 0f786bfa (the pool stays
   within the driver's heap) and 5c0469ae (the pool leaves room for the KV cache and state allocated later). Both
   are merged into PR #1 (47c8ec51), but every Vulkan number in the reply is from before that merge
   (dev 7df8c27c against b286167e).
2. **Vulkan + CUDA, prompt 2.** PR #1's bank gives the CUDA-only text (`1f019203…`), and dev's union gives
   `1bdc5d70…`. The reply's reading, "dev's union runs some experts through Vulkan", is wrong as stated. In
   final8's logs the Vulkan expert tier is off in every Vulkan + CUDA arm ("the CUDA expert tier is on and wins").
   What does run on the Vulkan device there is the dense matmul hook (`coli_v4_vk_matmul`: gate logits, the
   compressor and indexer projections), "dense matrices on the device (default)", in the union and bank arms alike.
   So the cause is still open.

Upstream dev has not moved past 61646cbd (checked 2026-10-24), so nothing needs rebasing.
