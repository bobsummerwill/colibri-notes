## Method (every arm)

- Harness `final6` ([tools/bench/final6/](tools/bench/final6/)): final5's runner and helpers (locks, clean builds,
  preflight, llama stop with an EXIT-trap restore, watchdog, per-sample evidence) with a per-arm model, context and
  client. Base environment = the docs' canonical serve line **without** `COLI_CUDA_MOE_BATCH` (`COLI_CUDA=1 COLI_GPU=0
  DSV4_CUDA_DEVICE=0 CUDA_DENSE=1 COLI_CUDA_PIPE=2 COLI_CUDA_ATTN_BATCH=1 V4_MOE_REFILL_GROUP=12 V4_LOADER_LANES=3
  V4_PREFIX_CKPT_DISK=0`, `--ram 40`); arms add switches on top.
- **A fresh server per sample**, the server's environment built from nothing (`env -i`), GPUs checked idle and free
  of foreign processes before each one, `nvidia-smi` sampled every 5 s.
- **Correctness = byte-identical text.** The engine is greedy only (it ignores `temperature`; there is no sampling code
  to test), so every arm in a group must produce the same bytes as the group's first sample. The full model has no
  older reference, so the references come from this run.
- **Speed = medians of 3 interleaved samples** after a discarded warm-up; time to first token for the prompt, tokens/s
  for decode.
- Every arm's premises (environment that must / must not be set, log lines that must / must not appear) are in
  `final6_tools.py`'s `ARMS` table and checked after each sample. Only A, B and V can abort the run (after the second
  failure); any other arm that breaks a premise is skipped and reported.
- Order: the question first, then the rest by value to the PR, so anything cut short is the least important.

**F18** (review finding, PR #2): the peer-compute path checks the peer for a fault only at the end, after the
primary's sync. The code catches a fault that is reported there, and its own comment says a faulted peer that never
releases the primary's wait would hang the sync. Only a simulated fault (`DSV4_CUDA_PEER_FAULT`, at the join) was ever
tested. The probe (`DSV4_F18_TRAP=n[:after]`, compiled only with `-DCOLI_F18_PROBE`) makes the n-th peer pass run a
`__trap()` kernel on the peer: a real sticky device fault, before the peer's down-projection (the primary's reduce
buffer would keep stale rows if its wait were released) or after it. `test_f18_trap_cuda.c` runs each case in a child
process with a 60 s alarm and classifies it: HANG, CAUGHT-CORRECT, CAUGHT-REFUSED, SILENT-WRONG or UNNOTICED, then
checks that the primary still computes correctly. It runs last in the window, so a faulted context cannot disturb
anything measured. If it hangs or goes wrong, the fix (a host-side wait on the peer's join with a timeout before the
primary queues its wait) goes into PR #2 before it is opened.

## Phase 2: DeepGEMM on computer4

DeepGEMM (sm_120a tensor cores) was never compiled or run in this project; it is the build RTX 50 users get. On a
DeepGEMM build `DSV4_MM_WARP` and `DSV4_MOE_EXPERT_MAJOR` are compiled out, so the question there is whether the rest of
PR #1 (bank sizing, routing books, the reserve) changes anything. Steps: DeepGEMM builds of dev, pr1 and pr2 with
CUDA 12.8 (the pinned sm120 port fetched by `tools/fetch_deepgemm.sh`); `dsv4-cuda-test` and the bitwise/bank tests on
the 5070 (any test over ~9 GB of VRAM skipped, Voxtype keeps its share); then, with the full model on computer4, dev vs
PR #1 in the default configuration (and with the bank if it fits in ~10 GB), interleaved as above.

## Results and how they reach the PR

Evidence: shadowfax `~/colibri-bench/final6/{pilot,bench}/` (per-sample logs, `nvidia-smi` series, texts, summary,
tarball). Then: manifests in `c/experiment_manifest.py` format for the A→B comparison (and the others with 3 samples per
arm) under `manifests/final6/`, validated, with hashed evidence; a comment on #2264 with the A/B table, the verify
count and a link here. If B is slower or not bit-identical in the default configuration, `DSV4_MM_WARP` defaults to 0
(opt-in) instead.

## What stays untested after all of this, and why

- **Windows build**: no Windows machine; upstream's CI Windows runner builds it when the PR's CI runs.
- **Two GPUs of different generations, or peer-to-peer without NVLink** (F21): the only two-GPU box has two 3090s with a
  bridge.
- **DeepGEMM on two GPUs**: computer4 has one card, so PR #2's two-GPU code on a DeepGEMM build.
- **Sampled decoding**: not a gap: the engine has none (greedy only).
